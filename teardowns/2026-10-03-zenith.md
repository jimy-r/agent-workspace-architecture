## What it is

Zenith is a mission harness from Intelligent Internet, published with a technical report, *From RALPH to Zenith*. The README names its target as "work that may run for days or weeks, where the dominant failure mode is *premature completion* rather than inability to make progress". One orchestrator session, running in Claude Code, Codex or Hermes, plans a mission into tasks and gates, spawns workers and validators as separate agent sessions, and stops only when a final reviewer agrees. The package is small, at seventeen Python modules, four role prompts and six bundled skills. This page reads the prompts, the runner and the report's source.

## What works

**The last reviewer is given only the request (pattern [11](../PATTERNS.md#11-a-scaffold-is-a-hypothesis--gate-it-behind-a-measurable-signal), partial).** When no runnable work is left, the runtime starts one more session. Its prompt is rendered from two values, the text of the original brief and the workspace path (`acp_runner.py`, `_render_terminal_reviewer_prompts`). The prompt tells it to review "as if you had no mission history" and adds that "earlier workers and validators are not proof" (`bundled/prompts/terminal-reviewer/system_prompt.md`). The mission is marked done only when that review returns done, and a gap goes back to the orchestrator as an attention item (`coordinator.py`, `_enter_terminal_review`). So the stop decision sits in code, with the one session that never saw the plan. Most review steps I've seen hand the reviewer the builder's account first. Mine did.

**A failure is traced to its cause before anything is retried.** On a failed task the orchestrator must "Identify the earliest invalid artifact", from a list that runs from the scope charter through the contract and the task body to the validation method. Then comes the rule I'd lift word for word. "Use `retry` only for a genuinely transient failed task where unchanged artifacts remain correct." A later line says "Repeated failure means inspect the method, not just the symptom" (`bundled/prompts/orchestrator/system_prompt.md`). A harness that re-runs whatever failed treats every failure as the builder's. This one asks first whether the brief was wrong.

**Checks are shown to run before the build starts (pattern [16](../PATTERNS.md#16-a-claim-carries-its-provenance-or-it-is-a-guess), partial).** The engineering playbook's third step, ahead of any contract, is "Prove validation readiness: confirm that the intended validation surfaces can actually run". Each assertion then carries an `Evidence:` line, "exact evidence a validator must collect" (`bundled/skills/engineering-mission-playbook/SKILL.md`).

The role prompts hold no mission facts, which arrive as the brief and template variables (pattern [1](../PATTERNS.md#1-pure-roles-composed-with-project-facts)). And the report prices every design it tests. Mean cost per task sits beside mean rank, from $22.21 for a single session to $407.58 for the RALPH loop, with Zenith at $175.68, and the report gives cost its own section rather than a footnote (pattern [15](../PATTERNS.md#15-price-the-lane-before-you-migrate-it)).

## The trade-offs

**The report's numbers are one run each.** Each task's table in the appendix lists nine runs. The four simpler designs ran once on each of two model stacks, and Zenith ran once on a hybrid of both. Eight tasks make seventy-two runs. The summary figure says "Models are averaged within each method before ranking", so Zenith's single run is ranked against the mean of two. I searched the LaTeX source for a repeat count, a spread or an interval and found none. The harness's own optimisation playbook says to "Characterize the noise before optimizing" and lists, among its anti-patterns, "Single-run win. Promoting on one measurement instead of enough repetitions to clear the noise band" (`bundled/skills/optimization-mission-playbook/SKILL.md`). The appendix prints clips so its examples are "inspectable without requiring access to the original machine or full trace logs". The repository holds the PDF, its source and nine figures, and the full traces and scoring code are not in it. So the headline, best mean rank at under half of RALPH's cost, can be read here and not re-run.

**The reviewer's independence rests on an instruction (pattern [7](../PATTERNS.md#7-a-cheap-hook-beats-a-careful-agent), partial).** What the reviewer is given is narrow by construction. What it can reach is narrowed by asking. Its session starts in the user's workspace (`acp_runner.py`, `run_terminal_review`), and the prompt carries a Forbidden Sources list of mission artifacts, contracts and validator reports it must not open. Pull request #33, opened on 2026-07-28 by a contributor with two merged fixes in the repository and still open at this reading, reports that the Claude adapter also loads the user's global instructions, settings and skill listings into that session before its first instruction. Its summary is "the reviewer's independence is currently prompt-deep only". That is the contributor's claim, and I haven't reproduced it.

**A failed gate can be waved through.** A `continue` decision on a failed task or gate sets its status to `cleared` (`controller.py`), and a dependent becomes runnable once every upstream reads `cleared` (`coordinator.py`). The orchestrator prompt knows. "Be especially careful with `continue`: for failed task or failed gate reports, runtime may treat `continue` as clearing that task." On that path the only guard is the prompt.

## What's conspicuously absent

**A bound on a run (pattern [3](../PATTERNS.md#3-make-silent-failure-loud-the-dead-mans-switch)).** This is a harness for work that runs for days, and the runner awaits each session's prompt with no timeout (`acp_runner.py`, `send_request`). The timeouts in that file cover short helper commands, process shutdown and server start. A dispatcher or reviewer that crashes is caught and reported (`coordinator.py`). A session that never returns is not. Money has no ceiling either. The report says the orchestrator reviews "cost, confidence, and requirement coverage", and its own Zenith runs cost between $60.05 and $499.77 each. A search of the harness source for "cost" and "budget" finds nothing.

**A measurement of the closing reviewer.** The report compares five designs and describes stopping as the orchestrator's decision. The word "terminal" does not appear in its source. So the mechanism I rate highest in the released code is one the project's own study never isolates, and nothing in the repository says how often that reviewer finds a gap the validators passed.

## What this teaches

Decide what your reviewer is given, and give it less. That costs one fresh session and a short prompt, and it transfers to any setup where one agent builds and another signs off. The harder half is knowing whether it earns its place, which this repository doesn't say. So measure it on your own closed work before you adopt it. I did, and the answer was narrower than the idea.

**What changed here:** I ran Zenith's closing review against fifteen finished tasks in my own workspace before adopting it. Each went to a reviewer that saw only what the task had asked for, which was its title, its instruction, its done-when and its write scope. I re-read every miss it reported.

Ten were experiment tasks whose criteria were a saved hash, a passing self-test and a result in tables. The blind reviewers confirmed no misses there. Five were build, patch and prose tasks, and two of those carried a real miss. A README said seven role assignments where the code declares nine. A patch was signed off on an independent check that had run on the version before a rework and never on the one kept. So the review is adopted for the second kind of task only, with a kill rule of fewer than one confirmed miss in the next ten.

The experiment reviewers found something my criteria had never asked for. Eight of the ten reported that I hash an experiment's protocol before the run and leave the analysis script unpinned, and in each case the script had been edited after the data came in. That rule changed the same day. Pull request #33 prompted one more check, on my own tool-free judge calls, which turned out to load none of my standing instruction files (4,456 input tokens against 59,697 through the default route). The record of these changes is this repo's [CHANGELOG](../CHANGELOG.md) entry for 2026-10-03, because the skill that carries them is not among the samples here.
