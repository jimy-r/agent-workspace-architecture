## What it is

GPT-RAG is Microsoft's solution accelerator for agentic retrieval-augmented generation on Azure, "Built on Microsoft Foundry with Foundry IQ as the default retrieval backend, Microsoft Agent Framework orchestration, Zero-Trust architecture and IaC" (repository description). This repository is the umbrella. It pins three component repositories and an infrastructure submodule in `manifest.json`, ships the azd template and the hosted-agent definition, and holds the decision records. The tree at this revision has 163 entries. 1,172 stars, MIT, 42 releases in the 90 days to 2026-09-06, in bursts. Nothing shipped between v3.7.0 on 2026-07-21 and v3.8.0 on 2026-09-03, then four releases landed in fourteen hours.

Two kinds of agent live here, and this page is mostly about the second. The product's agents run on Foundry. The engineering agents are the contract for coding agents working on the repository itself, and `AGENTS.md` calls itself exactly that, "This file is the stable, repository-wide contract for engineering agents". Three thin agent personas, four skills, four path-scoped instruction files, a validator and one compiled autonomous workflow.

## What works

**Every decision carries an expiry date and a list of things that would falsify it (pattern [11](../PATTERNS.md#11-a-scaffold-is-a-hypothesis--gate-it-behind-a-measurable-signal)).** The ADR template has a required "## Review trigger" heading, and the skill makes writing it a step: "Define fitness functions, adoption order, rollback or roll-forward, and a review trigger" (`.github/skills/architecture-decision/SKILL.md`). All five records comply. The retrieval-boundary decision says "Review this decision by **2026-11-04**, or earlier when any of these events occurs:" and lists nine events, one of which is "a cross-user authorization defect or unexpected managed-identity fallback is found" (`docs/adr/ADR-0003-microsoft-iq-retrieval-boundary.md`). That is a falsifier, not a calendar reminder. The template also forces a "### Do not change" option with its own benefits and costs, the cheapest always-on second lens I have seen, and half of pattern [13](../PATTERNS.md#13-challenge-half-formed-ideas-with-a-different-lens--and-hold-a-sample-back-to-prove-it-helps).

**Tiering by reversal cost, stated by verb (pattern [4](../PATTERNS.md#4-tier-by-mechanical-impact-not-by-tone)).** "Use an issue with acceptance criteria for local, reversible work. Record a decision under `docs/adr/` before implementing broad or high-risk changes" and "Release work requires explicit human approval before publishing a tag, release, package, image, or production deployment" (`AGENTS.md`). The irreversible acts are enumerated, not described by tone.

**Fail-closed in the code path, four directories from the rule that demands it (patterns [6](../PATTERNS.md#6-credentials-live-in-one-place-never-in-files) and [7](../PATTERNS.md#7-a-cheap-hook-beats-a-careful-agent)).** The security reference says "Security claims require evidence. Configuration or prompt instructions alone are not enforcement" (`.github/skills/engineering-principles/references/security-and-operations.md`). `config/continuity/settings.py` obeys it literally. Its `public_settings()` reads the environment and then overwrites two flags to `"false"` before returning, under the docstring "Return public settings while keeping validation-managed flags fail closed." No operator setting turns hosted continuity on. Only the setup path that verifies the live protocol version and both exact role assignments can. The contract schemas are pinned by sha256, and `.gitattributes` forces `eol=lf` on the schemas and the hash files alike, so the pin survives a Windows checkout. Most projects forget that line. I recomputed one hash at the revision and it matched.

**Provenance that reaches into the changelog (pattern [16](../PATTERNS.md#16-a-claim-carries-its-provenance-or-it-is-a-guess)).** "Agents deliver facts, artifacts, decisions, validation evidence, and residual risks rather than activity summaries" (`AGENTS.md`), and the v3.8.3 entry practises it: "UI and orchestrator pins are byte-identical to `v3.8.2` and were not revalidated", a release note that names which pins it did not re-check. The v3.8.2 entry publishes its own root cause. Two component repositories had shipped defects because "Neither had a workflow exercising the code that broke", and "The absence of these two jobs is the direct cause of both defects fixed in this release and in `v3.8.1`" (`CHANGELOG.md`).

**Platform behaviour documented at the point of use.** `hosted-agent/azure.yaml` carries, as comments beside the variables that work around them, four things an operator on Foundry will hit. The azd agent extension reads some fields without variable interpolation. `cpu` must be a quoted string. `APPLICATIONINSIGHTS_CONNECTION_STRING` is reserved and rejected because the platform injects telemetry itself. And two Azure Monitor resource detectors probe an instance-metadata endpoint the hosted sandbox does not have, so the failure can "surface later as an unhandled exception during live request handling (HTTP 500 on every /responses and /invocations call)". The flag that captures message content is off by default on purpose, because "capturing message content ships user prompts and model answers to Application Insights, which is a data-privacy decision each deployment has to make for itself." It is the most useful Foundry operations writing I have read, and it sits in YAML comments.

## The trade-offs

**Replication over reuse, across five repositories.** Each of the five repositories carries its own `AGENTS.md`, `copilot-instructions.md` and skill set, so an agent working in one needs no cross-repository access to load its full contract. The price is paid in the next section.

**1.7 KB of intent, 117 KB of generated guard.** The one autonomous loop is an issue-type classifier, a 1,724-byte GitHub Agentic Workflows source that compiles to a 116,972-byte lock file marked `linguist-generated=true` in `.gitattributes`. The compiler adds an egress firewall, digest-pinned images, SHA-pinned actions, token exclusion, a prompt-injection preamble, a daily AI-credit ceiling and issue-body sanitisation. The reviewable surface is the small file. The envelope is GitHub's work, and the credit here is for adopting a compiled workflow rather than for the envelope. As at 2026-09-06 the Actions API reports the workflow `disabled_manually`, with source and lock still committed on `main` and `develop`.

**Documentation on a separate branch.** "Product documentation remains on the `docs` branch" (`AGENTS.md`). The code tree stays lean, and `documentation-consistency` becomes a cross-branch discipline that no check in this tree can enforce.

## What's conspicuously absent

**A runner (pattern [8](../PATTERNS.md#8-audit-the-workspace-like-a-fitness-function), and the loud half of pattern [3](../PATTERNS.md#3-make-silent-failure-loud-the-dead-mans-switch)).** The tree holds fifteen test modules, about 300 KB. The six workflow files at the revision are a branch guard, a Copilot setup step, a docs deploy, the classifier source and its lock, and the asset validator. None invokes pytest or any other test runner, and the live Actions list has no test workflow either. The changelog entry above diagnosed this exact failure in the components. "The ingestion repository already contained 12 test files that no workflow ran" (`CHANGELOG.md`). The umbrella did not turn the diagnosis on itself.

The cost is concrete. `tests/test_release_contracts.py` hard-codes the release combination. It asserts `manifest["tag"]` equals `"unreleased"` and pins the orchestrator at `v4.0.2`, ingestion at `v2.7.0` and the UI at `v2.6.0`. `manifest.json` beside it reads `v3.8.3`, `v4.1.1`, `v2.7.3` and `v2.6.2`. Four of six assertions fail at the revision, and the same test sits on `develop` against the same manifest. The mechanism is the repository's own procedure. Step 2 of the release skill says "Update `manifest.json` `tag` to `vX.Y.Z`" (`.github/skills/multi-repo-release/SKILL.md`), and the test froze the values that step must change. `AGENTS.md` warns "Never copy version tables into agent instructions because they become stale." The one version table that was copied is the test that guards versions.

**A guard that covers the surfaces it fires on (pattern [17](../PATTERNS.md#17-one-canonical-copy-and-pointers-from-everywhere-else)).** The asset validator is real and well made. It checks frontmatter, a tool allowlist, duplicate skill names and local links, and it errors on an empty asset directory, a one-line dead man's switch. Its scope is three directories under `.github/`, from a `ROOT` set to the repository root. So `AGENTS.md` is the first entry in the workflow's path filter and is never opened by the script, whose `groups` tuple lists agents, skills and instructions only. `docs/adr/` holds two records numbered ADR-0003, the retrieval boundary dated 2026-08-04 and hosted continuity dated 2026-08-07, and ADR-0004 refers to "ADR-0003" by bare number on 49 lines, every one resolving by convention rather than by anything checked. And across the five repositories the three shared skills exist as fifteen files with fifteen distinct blob hashes and fifteen distinct sizes (sibling heads read 2026-09-06). The doctrine is stated in three files. The practice is five divergent copies, and the validator cannot see it by construction.

**A ledger check.** `v3.4.2` has a tag, a release branch and a 36-line changelog entry, and no published release, so the documentation site, which deploys on `release: published`, never rebuilt for it. `v3.0.0` and `v2.9.17` were published and have no changelog entry; the file steps from v3.0.1 to v2.9.16. `.github/copilot-instructions.md` lists "Update `CHANGELOG.md`" among the release responsibilities and says "The GitHub Release notes and the changelog must agree." Three set differences, tag against changelog against published release, would have caught all three.

**Any evaluation of the product.** A path search of the tree for eval, bench, golden or groundtruth returns one hit, and it is an ADR filename. The testing reference names the gap itself: "Do not treat a successful deployment as sufficient evidence when the change affects authorization, data correctness, retrieval quality, or upgrade behavior" (`.github/skills/engineering-principles/references/testing-and-evidence.md`). Retrieval quality is listed as needing evidence, and nothing in the tree produces any. For a reference implementation on Foundry, this is the absence that matters most.

**Review dates on the agent layer itself.** Five decision records carry expiry dates and falsifiers. The three agents, four skills and four instruction files carry none. Pattern 11 is applied to the architecture and never to the scaffolds.

## What this teaches

A check you do not run is a comment. The whole culture of fitness functions is here, with FF-1 to FF-5 named in a decision record, a validator in CI, 300 KB of tests and a changelog that explains root causes. What is missing is a runner, and the artefact that drifted is the verifier. Two smaller rules follow. A validator inherits the boundary of the tree it runs in, so a repository-local script guarding a surface that spans five repositories covers a fifth of it and reports green. And a CI trigger is not a check, because a path filter can make a job look broader than what its script reads.

Three lifts transfer for an afternoon each. Pin the bytes and pin the line endings that keep the bytes stable. Give every decision record a review date and a list of falsifiers, then give the same to your instruction files. And run a three-way set difference, tag against changelog against published release, on every release. That last one belongs in this repository's own release ritual too, which has the same three artefacts and, until now, the same gap.
