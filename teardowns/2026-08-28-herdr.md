## What it is

herdr is "the runtime your coding agents live on", a single Rust binary that runs as a background server and owns the terminals your agents run in. Terminals keep running when you close the client or lose the connection. After a server restart the processes are gone, but herdr restores the layout, and agent conversations resume where the agent supports it. Every pane carries an agent state (the README names working, blocked and idle, and the API adds done and unknown), and agents drive the runtime themselves through a CLI and socket API, spawning panes, prompting each other, and waiting until another agent is genuinely blocked. At about 41k stars it is one of the most widely adopted pieces of agent infrastructure going, and it deliberately wraps nothing. Claude Code, Codex, Cursor and the rest run unmodified inside it.

## What works

**The pane state model is the right primitive.** Working, blocked, idle, surfaced per pane, with "never hunt for the stuck one" as the promise (`README.md`). That is the classify-then-act shape (pattern [2](../PATTERNS.md#2-classify-then-act-not-ask-then-wait)) applied to operator attention. The runtime classifies, and the human acts on the one that needs them. Anyone who has run six agents in six terminals knows this is the actual daily problem, and herdr made it the centre of the product rather than a dashboard afterthought.

**Agent-native control is ahead of the field.** The socket API's wait-until-blocked semantics give agents a real coordination primitive. An orchestrating agent can hand work to another pane and block on genuine need rather than polling or guessing (pattern [14](../PATTERNS.md#14-delegation-is-a-queue-you-fill-not-work-the-agent-finds)'s delegation mechanics, provided as infrastructure). Most multi-agent coordination today is prompt-mediated hope. herdr made it a syscall.

**Persistence as a deliberate stance.** Always-running is a considered answer to the loop-selection question (pattern [12](../PATTERNS.md#12-loop-selection-not-everything-should-be-a-loop)), not an accident. The runtime exists precisely so sessions outlive the terminal that started them, reattachable from anywhere including over SSH. One binary, no Electron, is the same discipline applied to the dependency surface.

## The trade-offs

**Owning the terminal buys legibility and pays in responsibility.** Because herdr owns every agent's terminal, it is positioned to see everything, from what ran to what it cost and what changed. At this revision it spends that position almost entirely on liveness and attention. That is a defensible sequencing choice for a runtime finding adoption, but it means the layer best placed to account for agent work currently accounts only for whether it is stuck.

**Detach-and-walk-away moves the trust boundary.** The pitch is close the lid and let them keep working. Unattended operation is exactly where the runtime's visibility matters most, and where the absences below stop being theoretical.

## What's conspicuously absent

**Spend visibility (pattern [9](../PATTERNS.md#9-context-is-a-budget-not-a-constant)), and users are asking for it.** A user opened discussion #2746 with the failure that makes the case. A builder ran eleven fix rounds, re-reading roughly 650k tokens of context each round, before anyone noticed. The same user had first filed it as a feature request (#2742), which the project's triage bot closed within two minutes as outside the bug tracker and pointed to the Ideas board. The replies in #2746, from me and one other participant, worked through where a cross-round budget should live, launch-gate floors versus mid-turn kills, ledgers, and alert design. No maintainer has posted in the thread. Community plugins have started on the problem, with cost badges on each pane, usage dashboards and a run ledger. But at revision `7b675f42af35` the runtime itself keeps no per-run ledger, budget or spend trend. In the thread I argued that the budget belongs to whatever owns the loop. The runtime is still the one layer that sees every pane, which makes it the natural home for the ledger that budget would read.

**A dead-man's switch over always-running agents (pattern [3](../PATTERNS.md#3-make-silent-failure-loud-the-dead-mans-switch)).** herdr tells you when an agent is blocked. Nothing tells you when an agent that should have produced something has quietly produced nothing, which is the failure mode that always-running infrastructure inherits the moment users take the promise to detach and walk away seriously. Liveness is not freshness.

**An audit trail for unattended work (pattern [16](../PATTERNS.md#16-a-claim-carries-its-provenance-or-it-is-a-guess)).** After a detached weekend, the questions are what each agent did, what it touched, and on whose instruction. Pane scrollback is not an answer. Scrollback is where provenance goes to die. A runtime that owns the terminal is the natural writer of an append-only record of unattended work. At this revision the nearest thing in the runtime is a rotating diagnostic log (`src/logging.rs`, capped at 5 MB, with no older files kept).

**A fitness function for the fleet (pattern [8](../PATTERNS.md#8-audit-the-workspace-like-a-fitness-function)).** With a state for every pane now, and costs eventually, the runtime holds most of what it would need to say this fleet is healthier or sicker than last week. It rolls the current pane states up to each workspace (`src/workspace/aggregate.rs`), but nothing turns them into a trend.

## What this teaches

The runtime layer is consolidating faster than the accountability layer. herdr has effectively won the "where do agents live" question for a large slice of the ecosystem, and what it lacks is the layer the runtime itself hasn't shipped, the one holding budgets, ledgers, freshness sentinels and the provenance of unattended work. Plugins have started on the spending half. Discussion #2746 shows users asking for that layer in public, with no maintainer response so far. The transferable lesson for any workspace is to put the accounting where the loop lives. Per-turn visibility can never see an eleven-round runaway, and whichever layer owns the loop owns the responsibility for the number.

## Corrections

- **2026-09-27.** An earlier version said herdr's maintainers took part in the design discussion in #2746. None did. A user opened the thread, and the replies came from me and one other participant. The three passages that said otherwise have been corrected. A re-check the same day read the whole tree at this revision and at v0.9.1, and confirmed the four absences in the runtime. It also found errors, now corrected. The page said nobody had shipped the accounting layer, but third-party herdr plugins had shipped per-pane cost tracking, a run ledger and a session recorder before it was written. It said sessions survive restarts, echoing the README at this revision, where herdr's own docs say a server restart restores the layout but not the processes. It credited the runtime with per-pane uptimes it doesn't hold, said nothing aggregates pane state when the runtime rolls it up per workspace, and missed the diagnostic log. The spend paragraph now matches the position I took in the thread, that the budget belongs to whatever owns the loop, and the star count is updated.
