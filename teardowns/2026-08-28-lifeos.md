## What it is

LifeOS is Daniel Miessler's "Life Operating System", a general-purpose AI harness layer that captures who you are (the TELOS interview), holds your goals as current-state versus ideal-state, and rides on top of whatever coding harness you already run. The hooks that run on every turn are wired on Claude Code only for now. Other harnesses get the skill, your data, Pulse and context loading in every session (`LifeOS/INSTALL.md`). At about 19k stars it is one of the most-adopted personal AI operating layers in the ecosystem, and it ships as a single self-contained skill whose agentic installer sets up the whole system.

## What works

**The distribution discipline is genuinely good.** The entire system ships as one `LifeOS/` directory holding the orchestrator, the workflows, the install payload and the bootstrap script (`LifeOS/SKILL.md`, "How it ships"). The skill file is explicit that nothing ships outside it, and it names its single sources of truth for both install paths. It even documents its own versioning trap: the skill's component version and the release version are different numbers, and the file tells the reader never to confuse them. That is one-canonical-copy thinking (pattern [17](../PATTERNS.md#17-one-canonical-copy-and-pointers-from-everywhere-else)) applied to distribution, and most projects at this scale don't have it.

**Capability states are honest.** The `doctor` route prints one of four states for every capability (live, broken, declined or stale), with the exact fix command for anything broken. The instruction that follows is the best line in the file. A declined capability is "a legitimate way to run LifeOS, never a defect to nag about". Respecting *declined* as a first-class state, distinct from *broken*, is a design courtesy most installers never extend.

**Hooks are wired with permission, per step.** The installer (`Tools/InstallHooks.ts`, `Workflows/Setup.md`) asks before it touches anything, and setup always precedes the interview so guardrails exist before personal data flows. The skill/workflow routing table is clean pattern-1 composition: five triggers, five targets, no ambiguity.

**Stored facts carry their source.** The memory reviewer (`LIFEOS/TOOLS/MemoryReviewer.ts`) requires every stored fact about you to carry a provenance tag, `~explicit` if you stated it, `~deduced` if it follows logically from what you stated, `~inferred` if the agent noticed a pattern. Transcript captures pass through an envelope that binds source, channel, session and capture time to the content. When two stored facts disagree and nothing settles which is true, the reviewer may not pick a winner, because "a guess written as ~explicit is later read as 'the principal said this'". `StateEvidence.ts` gathers observed data on health, activity, work and money so that your own claims about your current state get checked against what actually happened. And the `VerificationGate` stop hook applies the same idea to the agent's reports about its own work ("THE MESSAGE IS A CLAIM; THE TRANSCRIPT IS THE EVIDENCE"). For a system whose product is statements about your life, this is provenance (pattern [16](../PATTERNS.md#16-a-claim-carries-its-provenance-or-it-is-a-guess)) treated as a first-class concern.

**The eval machinery is real.** The Evals skill (`install/skills/Evals/`) is an assertion-first framework with typed deterministic asserts, an LLM judge, capability and regression suites, and a trial runner that reports pass rate, mean score, standard deviation, pass@k and pass^k over n trials (`Tools/TrialRunner.ts`). Since v7.28.3 (2026-08-01), a PostToolUse hook, `ConfigEvalFire`, runs a behavioural regression suite whenever a file that defines behaviour changes (the system prompt, an identity file, `CLAUDE.md`, the operational rules or any hook) and notifies on regression. It never blocks the edit.

## The trade-offs

**Install-by-prompt is the new `curl | bash`.** The primary install is "give this document to your AI and say install this", and the document itself (`LifeOS/INSTALL.md`, which the project's site renders for humans and AIs) carries a literal `curl | bash` line. It is honest about what it is, and permission-gated at each step, but it normalises handing an agent a remote document with instruction-following authority. Discussion #1715 has a live example. One user's own assistant was wary of the `curl` step and wanted to check whether the LifeOS site was a typosquat, and once pointed at the thread's quality reports it recommended against upgrading at all. The v7.40.4 release notes take the point ("one user's DA even flagged our own installer as suspicious before recommending against upgrading. Fair."). That assistant improvised the read-before-install gate the ecosystem hasn't standardised yet. The trade is real reach (any harness, one prompt) against training users to pipe documents into agents, and LifeOS at least makes the trade visibly.

**An always-loaded personal OS is a standing context spend, and LifeOS meters it.** LifeOS adds a permanent instruction surface (system prompt, algorithm, skills, hooks) to every session of the harness it rides on, on the README's premise that full context makes everything better. The project manages that bill in the open. The v7.0.0 release cut the always-loaded doctrine from about 88KB to 28KB "so every turn is faster and sharper", and a human-gated `Trim` skill shrinks any standing file that grows too big. A nightly Pulse job prunes applied proposals that had piled up in those files, memory files are capped at 48 entries of 256 characters, and `TokenXray` shows "what each kind of context costs once re-read every turn". The spend is still real. When #1715 reported that v7 felt worse, prompt-surface size was one of the three suspects the maintainer offered to bisect.

## What's conspicuously absent

**Cases for the behaviour the product sells (the unbuilt half of pattern [11](../PATTERNS.md#11-a-scaffold-is-a-hypothesis--gate-it-behind-a-measurable-signal)).** Discussion #1715 is the public argument over whether v7 is worse than v5, and it ran on evidence users gathered themselves. Several said v7 "feels" worse. One compared 33 v5 sessions with 25 v7 sessions and found memory searched in 88% of the first and 40% of the second, with the Algorithm never opened in 15 of the 25. The same user reported six sessions opened with a byte-identical instruction, four of which ran the Algorithm and two of which didn't. A community eval with a confidence box followed, at one or two trials for most cells. The maintainer asked for a concrete before/after pair to bisect, then pointed at the latest release. No result from the shipped framework appears in the thread, and the shipped cases don't reach the question. They test general habits (lead with the answer, verify before claiming done, read before editing, don't invent paths), with the disposition suite at two trials per case because it fires on every edit to a behaviour file. None of them checks whether the Algorithm runs or memory gets consulted, the two behaviours users ended up counting by hand.

**A dead-man's switch that runs by default (the unbuilt half of pattern [3](../PATTERNS.md#3-make-silent-failure-loud-the-dead-mans-switch)).** LifeOS has written the switch and ships it switched off. `PULSE/checks/poller-meta-monitor.ts` names the trap in its own header ("Pulse's default behavior is to silently skip jobs after 3 consecutive failures") and "screams loudly if any monitored job has been silent beyond 3× its schedule". The public Pulse template doesn't schedule it. Its own note says monitors belong in the private user layer ("User-specific monitors belong in PULSE.user.toml"), and a code search of the repository finds no other reference to the file. A fresh install gets `doctor` (a pull diagnostic), heartbeats on the Pulse hooks page, nudges when a broken capability trips, and a health check every five minutes that probes whichever websites you list, none by default. Pulse itself is optional. On a default install, nothing scheduled watches for the failure the monitor's header describes.

## What this teaches

Four things transfer. Distribution as a single self-contained artifact with named sources of truth is worth stealing at any scale. Treating declined as a first-class state deserves adoption by every installer that gates capabilities, because an operator who said no is not a bug. Provenance tags on stored facts, together with a refusal to settle a conflict nobody can source, are the cheapest defence a memory system has against its own guesses hardening into facts.

The fourth is about coverage. LifeOS shipped its trial runner with v6.0.0 on 2026-07-02, four weeks before #1715 opened, so the instrument was there when users said the new version was worse. It had no case for the behaviours they meant, and the argument ran on counts gathered by hand. An eval framework answers only the questions it has cases for, so write the cases for the claim you sell before your users have to.

The review, two weeks before this page, led to a split between gates that block and gates that only advise (from `ISAGate`), tags recording how each standing rule is enforced, and the two rules on evidence modality in the [verify-completion sample](../samples/.claude/skills/verify-completion/SKILL.md) (from `VerificationGate`). ## Corrections

- **2026-09-27.** The first version of this page read the README, `LifeOS/SKILL.md` and two directory listings, and missed the install payload under `LifeOS/install/`, where most of the system lives. Its four absence claims were wrong or overstated at the pinned revision itself. It called measurement absent, but the payload ships an eval framework that reports pass rates with variance, and a hook that runs a regression suite on every edit to a behaviour file. It called provenance absent, but stored facts carry source tags. It said nothing priced the standing context, but the v7.0.0 release notes record a two-thirds cut to it and Pulse computes the cost of each session. It described `doctor` as the only failure check, but a monitor for silently skipped jobs ships, unscheduled. It also misread discussion #1715 twice. The typosquat check came from a user's assistant and ended in advice not to upgrade, where the page had a user checking and then installing. The six identical sessions split 4/2 on whether the Algorithm ran, where the page said outcome. The page has been rewritten against the full payload at the same revision, the star count is updated, and "What changed here" now records the changes an earlier review of LifeOS had already made here.
