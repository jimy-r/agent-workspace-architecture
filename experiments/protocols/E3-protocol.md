## Protocol

- **Question.** In the longest main-thread sessions, what would compaction have cost and saved in API-equivalent dollars had it fired at every task boundary, or at a lower context threshold than the live one?
- **Sample.** Every main-thread transcript (a `*.jsonl` file at the top of the Claude Code project folder for `<workspace>`, which the script resolves from `session_report.PROJECT_DIR`) whose first request falls on a local date from 2026-08-29 to 2026-09-28, and which has 300 or more assistant turns or a peak context of 300,000 tokens or more. A turn is one request, meaning one assistant message id with a usage record and a non-zero context, deduplicated as `cache_write_scan.load_steps` does. Keep-alive tick requests count as turns, and the Result also gives the count without them. Context is cache read plus cache write plus uncached input (`cache_write_scan.ctx`). Interactive and headless sessions both count, and the Result gives the split. Transcripts are read as they stand at run time.
- **Imports.** Request parsing (`load_steps`, `ctx`, `parse_ts`) comes from `scripts/cache_write_scan.py`, and tick detection from `scripts/context_growth.py` (`is_keepalive_tick`, plus `keepalive_filter.tag_tick_steps`, which it imports). Prices come from `scripts/tier_metrics.py` (`price_per_million`, `family_of`, `CACHE_READ_MULTIPLIER` and `CACHE_WRITE_MULTIPLIER["main"]`), applied per request at the request's model family. None of them is edited or retyped. Every figure is reported in tokens and in dollars.
- **Genuine user message.** A user record whose content carries text and no tool result. Keep-alive ticks are excluded, as are records flagged `isMeta`, `isCompactSummary` or `isSidechain` and texts that open with a harness tag (`<task-notification>`, `<local-command-stdout>`, `<local-command-stderr>`, `<local-command-caveat>`, `<system-reminder>`, `<bash-stdout>` or `<bash-stderr>`). A typed slash command counts.
- **Boundaries.** The user fixed three kinds before the data (ruling of 2026-09-28).
  1. *Wrap.* An assistant `Skill` call whose `skill` input is `wrap`, or a genuine user message carrying the `/wrap` command (`<command-name>/wrap</command-name>`). Its anchor is the first genuine user message after it.
  2. *Todo block.* An `Edit`, `MultiEdit` or `Write` call on `<workspace>/tasks/todo.md` (or the relative `tasks/todo.md`) whose new text adds a line opening `# Session`, the file's session-block heading, that its old text lacks. A `Write` counts when its content holds such a line. Its anchor is the last genuine user message at or before the call, the one that opened the task the block records.
  3. *Idle gap.* A genuine user message sent more than 60 minutes after the last assistant record outside a keep-alive tick window. It is its own anchor.

  A boundary compacts immediately before the first request after its anchor, and signals that share that request make one boundary. A boundary is skipped when no request follows its anchor, when a real compaction sits between that request and the one before it, or when the context to be compacted is no larger than the new prefix (floor plus summary). The Result counts signals by kind, the boundaries they make and each skip reason.
- **Real compactions.** A real compaction event is a record flagged `isCompactSummary` or a system record of subtype `compact_boundary`. Such records with no request between them are one event. The trigger (auto or manual) and the pre-compaction token count come from the boundary record's metadata where present. Otherwise the trigger is unknown and the pre-compaction size is the context of the last request before the event plus that request's output. Records of type `summary`, which `load_steps` also treats as compaction markers, are counted in the Result and are not events.
- **Floor and summary size.** A session's floor F is the context of its first request. When a compaction summary precedes that first request (a continued session), F is instead the median floor of the other sample sessions. Every real compaction with a request on each side, in any main-thread transcript of the window whether sampled or not, gives S_event, the context of the first request after the event minus the file's F. S_event covers the summary and anything the harness re-attaches with it. Every simulated compaction uses the median S_event as its summary size S. The Result reports the count, quartiles and extremes of S_event, with the summary text's length in characters beside it.
- **Live point L.** 465,000 tokens, which is 93% of the 500,000-token `autoCompactWindow` that `get_usage` reported on 2026-09-28. The Result lists every auto-triggered real compaction with its date and pre-compaction size. If 3 or more auto compactions fall on 2026-09-15 to 2026-09-28 and their median pre-compaction size sits more than 5% from 465,000, the run uses that median as L and records the change.
- **Costing a compaction** (card constraint). A simulated compaction before request j reads the full prefix once (the arm's context at request j-1), emits S tokens of summary as output, and then writes the new prefix F + S at the main-lane write multiplier, all priced at the model of request j-1. The cache is cold when more than 60 minutes separate request j-1 from the compaction (the main thread's 1-hour TTL, live since 2026-08-29), timed at request j for a simulated compaction and at the event record for a real one. A cold prefix cannot come from cache, so it is priced at the write rate. The card's literal price, a cache read even when cold, is a sensitivity. The summarisation call of a real compaction is assumed to leave no usage record in the main transcript [unverified, and the Result reports the check]. The as-run arm is therefore charged for each real compaction by the same rule, reading its pre-compaction prefix and emitting S_event as output. Its new-prefix write is already in the next request's usage. If the check finds the call logged as a request, the as-run arm keeps that request, drops the modeled charge, and the Result says so. Either way, each arm pays for every compaction it makes.
- **Replaying requests.** An arm changes only the context each request carries. Output and uncached input stay as run. After a compaction before request j, a later request i in the same stretch of the as-run transcript carries `X_i = F + S + (C_i - C_{j-1})`, where C is the as-run context. Its tokens split three ways.
  - Request j reads the new prefix F + S that the compaction wrote and writes the rest, provided it runs the model of request j-1. Otherwise it is priced as cold.
  - A warm request is one whose as-run cache read reached at least `C_{j-1}`, past the history that was summarised. It keeps its as-run write, and its cache read shrinks by the tokens removed.
  - A cold request is one whose as-run cache read stopped short of `C_{j-1}`, as an idle-gap, model-switch or tool-change re-write does. It reads from cache at most F (its as-run read, capped at F) and writes the rest.

  With no simulated compaction every request keeps its as-run split, so the as-run arm reproduces the usage-priced cost exactly.
- **Arms.**
  - *As run.* The usage-priced cost of every request, reported alone and with the modeled real-compaction calls added. The second figure is the H1 baseline.
  - *Boundary (B).* As run, plus a compaction at each boundary. Real compactions stay where they happened. Each is charged at the arm's own pre-compaction context, and the arm then re-aligns with the as-run context.
  - *Threshold (L, 200k, 300k, 400k).* Real compactions are undone, and the context runs on from the previous request as if the event had not happened. The first request after an undone event reads its whole prefix and writes nothing new when warm (60 minutes or less after the previous request, on the same model), and follows the cold rule otherwise. A compaction fires before request j when the arm's context at request j-1 plus that request's output reaches the threshold, and that context exceeds F + S. L is the H2 baseline.
- **Model check.** Over the sample sessions with at least one real compaction, every one of them auto-triggered within 5% of L, the pooled dollars of the L arm against the as-run arm with modeled calls.
- **Scope and safety.** Main thread only, so subagent transcripts are out of scope. Transcripts are opened read-only and only inside the script. No transcript text leaves the script or reaches a model. Output goes to `tasks/experiments/E3/`.

## Hypotheses

- **H1, boundary compaction.** For each sample session, saving_B = 1 - cost(B) / cost(as run with modeled calls). The median saving_B across the sample is 20% or more.
- **H2, lower threshold.** For each threshold T of 200k, 300k and 400k, saving_T = 1 - cost(T) / cost(L) per session. The median saving_T across the sample is 10% or more for at least one T. Pooled savings, token savings and each arm against the as-run arm are reported beside the medians without a verdict.

## Decision rules

- **Sensitivity.** Each hypothesis is scored under the primary pricing and under three sensitivities. Two set S at the 25th and at the 75th percentile of S_event, and the third is the card-literal cold read (every compaction's prefix at the cache-read rate). It is PASS when its statistic clears the threshold under all four, FAIL when it misses under all four, and INCONCLUSIVE otherwise.
- Both hypotheses are INCONCLUSIVE when the sample holds fewer than 5 sessions or fewer than 3 real compactions yield an S_event.
- H2 is INCONCLUSIVE when the model check covers 3 or more sessions and the L arm misses the as-run arm by more than 10%.
- No verdict adopts a change. A PASS on either hypothesis is evidence for running the fidelity half (probe recall at least 90% of the full-context baseline) before compaction behaviour or `autoCompactWindow` changes. A FAIL on H2 is evidence to keep the live threshold at the 2026-10-02 autocompact-ceiling review. A FAIL on H1 is evidence against boundary compaction as a cost lever at current prices. The main thread merges the figures into `Reference/token-discipline-measurements.md` and the scaffold register.

**Quality guard.** None in this half. It is offline and changes no behaviour, and the fidelity half is the quality guard.

**Budget.** No model spend beyond the build agent.
